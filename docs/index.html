1. Antes de empezar

1.1 Qué es la ICD API

La ICD API es una API REST que da acceso programático a la Clasificación Internacional de Enfermedades de la OMS. No es un «buscador» suelto: es la fuente de verdad que alimenta el ICD-11 Browser, la herramienta de codificación y el motor DORIS de la OMS, y expone exactamente la misma información en formato JSON-LD.

Datos clave de la ICD API
Dato Valor
URL base https://id.who.int/
Versión de la API 2.6 (enero de 2026)
Cabecera de versión API-Version: v2 (solo el número mayor)
Autenticación OAuth 2.0, client credentials
Endpoint de token https://icdaccessmanagement.who.int/connect/token
Ámbito (scope) icdapi_access
Formato de datos JSON-LD (application/json o application/ld+json)
Duración del token ~1 hora

La versión 2 es compatible hacia atrás con la 2.x: el código escrito para 2.x no necesita cambios. Lo único que hay que hacer es enviar la cabecera API-Version: v2, porque sin ella la API responde con el formato de la versión 1.

RDF/XML, que sí estaba soportado en las primeras versiones, está deprecado desde la 2.3.

1.2 Alcance: Fundamento, linearizaciones e ICD-10

La API expone tres cosas distintas que se confunden con frecuencia. Distinguirlas es el paso más importante antes de escribir código:

Las tres capas de contenido de la ICD API
Capa Qué es Dónde vive en la API ¿Tiene códigos?
Fundamento
(Foundation Component) 		El universo completo de la OMS-FIC: enfermedades, trastornos, lesiones, signos, descripciones funcionales, intervenciones y códigos de extensión. Puede haber varios padres para la misma entidad. /icd/entity/... No
Linearizaciones
(listas tabulares) 		Un subconjunto del Fundamento con una finalidad concreta, donde las entidades son mutuamente excluyentes y tienen un solo padre. /icd/release/11/... Sí
ICD-10 Las ediciones clásica de la ICD-10. /icd/release/10/... Sí

Las dos linearizaciones disponibles son:

  • mms — ICD-11 para Mortalidad y Morbilidad (MMS). Es la que necesitas siempre que necesites códigos y la estructura tal y como aparece en la ICD-11 publicada.
  • icf — Clasificación Internacional del Funcionamiento, la Discapacidad y la Salud (ICF).

Aviso importante. Si estás construyendo una herramienta que necesita códigos ICD-11 con la estructura que muestra la ICD-11 publicada (https://icd.who.int/browse11), tienes que usar los endpoints de linearización con linearizationname=mms. El Fundamento no tiene códigos ni excluye entidades entre sí: no sirve para codificar.

1.3 Requisitos previos

  • Una cuenta en https://icd.who.int/icdapi (el registro es gratuito).
  • Las credenciales clientId y clientSecret, que obtienes con el enlace «View API access key» una vez dentro del portal.
  • Un cliente HTTP cualquiera. Todos los ejemplos de esta guía usan curl, Python y JavaScript.

2. Autenticación OAuth 2.0

2.1 Obtener las credenciales

  1. Regístrate en https://icd.who.int/icdapi mediante el enlace [Register].
  2. Inicia sesión en el portal.
  3. Pulsa «View API access key». Verás tu clientid y clientsecret.
  4. Puedes crear y revocar varios clientes por usuario, pero para un uso normal uno basta.

No pongas el clientsecret en el código fuente ni en un repositorio. Léelo de un gestor de secretos, de variables de entorno o de un almacén cifrado.

2.2 Solicitar el token

La API usa OAuth 2.0 con el tipo de concesión client credentials (RFC 6749). La petición es un POST a https://icdaccessmanagement.who.int/connect/token con:

  • Autenticación HTTP Basic con clientId:clientSecret.
  • grant_type=client_credentials.
  • scope=icdapi_access.

La respuesta es un JSON con el token y su caducidad:

2.3 Ciclo de vida del token

El token es válido aproximadamente una hora. En la práctica:

  • Cachéalo y reutilízalo entre llamadas. Pedir un token por cada consulta duplica tu tráfico y te hace más susceptible de que la OMS limite tu cuenta.
  • Guarda expires_in y renueva antes de que caduque (por ejemplo, a los 50 minutos).
  • Trata un 401 como señal de token caducado: pide uno nuevo y repite la petición una sola vez. Un 401 casi nunca significa que el recurso no existe.

3. Cabeceras obligatorias

3.1 Las cuatro cabeceras

Las cuatro cabeceras obligatorias de la ICD API
Cabecera Valor Obligatoria Para qué sirve
Authorization Bearer <access_token> Sí Autenticación OAuth 2.0. Sin ella: 401.
Accept application/json o application/ld+json Sí Selecciona el formato JSON-LD.
Accept-Language es Sí Selecciona la versión en español del texto.
API-Version v2 Sí Selecciona la versión 2 de la API. Solo el número mayor.

Accept-Language es la cabecera que hace todo el trabajo de la edición en español. Acepta códigos ISO 639-1 (en, es, fr, pt, zh…) y también admitirá prioridades al estilo es,es-ES;q=0.9,en;q=0.8, aunque lo sencillo y lo que la OMS documenta es un único código.

Los resultados de búsqueda se devuelven en JSON plano, no en JSON-LD, aunque se pida application/ld+json. No es un error: es el comportamiento documentado de la API.

3.2 HTTPS y URI de la clasificación

Todas las comunicaciones van cifradas: solo se admite https. Las peticiones http se redirigen automáticamente, pero la OMS recomienda llamar directamente a https porque funciona más rápido (ahorras el salto de redirección).

Hay un detalle que sorprende la primera vez: las URI de las entidades de la clasificación llevan http, porque son identificadores estables y no URLs de la API. Por ejemplo, la URI del Fundamento para el cólera es http://id.who.int/icd/entity/257068234. Esa misma URI es el endpoint de la API que devuelve la ficha de esa entidad.

Regla práctica: reescribe http://id.who.int/... a https://id.who.int/... antes de llamar. No lo hagas con una sustitución ciega sobre datos que vengan de la API: hazlo solo en la capa que construye URLs de peticiones.

Conclusiones prácticas que ahorran mucho tiempo:

  • El español en MMS existe desde la versión 2020-09. Las versiones 2019-04 y 2018 solo tienen inglés. Si necesitas una versión muy antigua, no hay texto en español disponible.
  • El español en ICF existe desde la versión 2025-01. En 2024-01 la ICF solo está en checo, inglés y turco. Antes de 2025-01 la ICF no tiene traducción al español (y en 2023-01 y anteriores la ICF ni siquiera está disponible en la API).
  • El Fundamento está disponible en todas las versiones, pero la traducción puede ser parcial: la OMS advierte que si un idioma no está disponible en todas las clasificaciones, su traducción en el Fundamento también puede estar incompleta. No des por hecho que todo el Fundamento está traducido al español.
  • La ICD-10 no tiene versión en español. Las ediciones ICD-10 disponibles (2019, 2016, 2010 y 2008) están solo en inglés, y la de 2008 además en francés.

4.3 Verificar los idiomas disponibles en vivo

No te fíes de una tabla: la API te dice exactamente qué hay en cada versión. Desde la versión 2.6 el endpoint de primer nivel del Fundamento y los de linearización incluyen información de idiomas y versiones.

En la respuesta encontrarás dos campos clave:

Campos de idioma en la respuesta de una linearización
Campo Significado
availableLanguages Todos los idiomas disponibles para esa linearización, incluidos los que están en prerelease.
prereleaseLanguages Subconjunto de los anteriores: los que aún no son una traducción estable.

En el Fundamento (/icd/entity) hay dos campos equivalentes:

Campos de versión e idioma en la respuesta del Fundamento
Campo Significado
availableLanguages Todos los idiomas disponibles en alguna linearización (no solo en la que te interesa).
allReleases Todas las versiones desplegadas en la API.
supportedLinearizations Las linearizaciones disponibles a partir de ese Fundamento.

Si es no aparece en availableLanguages de la linearización que te interesa, esa combinación de versión e idioma no existe. Cambia de releaseId o de linearización.

4.4 Consideraciones al buscar en español

  • Los términos de búsqueda van en el idioma que quieres que se busquen. La API busca en los títulos, sinónimos y nombres completamente especificados de la versión del idioma solicitado. Buscar «diabetes mellitus tipo 2» con Accept-Language: es encuentra la entidad española; con Accept-Language: en buscarías la entidad inglesa (que puede ser otra URI).
  • Las entidades no se traducen «en el sitio»: son entidades distintas por idioma. El título español y el inglés de una misma categoría suelen tener URIs distintas en la API. Si guardas URIs, guárdalas junto con el idioma con el que las obtuviste.
  • Tildes, ñ y diacríticos. La API no normaliza de forma mágica: si el texto indexado en español lleva tilde (cólera) y tú envías colera, el resultado puede no aparecer. Prueba ambas formas, o usa el comodín % al final de la palabra (ver la sección 7).
  • Los sinónimos en español están indexados. En la ICD-11 MMS en español, muchas entidades tienen sinónimos traducidos; buscar un término habitual de tu país tiene más probabilidades de acertar que buscar el título oficial.
  • Las definiciones también están en español cuando la traducción de la versión lo cubre. Para buscarlas hay que desactivar el modo de codificación médica (ver medicalCodingMode en la sección 7).

6. Recetas prácticas

6.1 Buscar un término en español

Variables útiles:

  • q — el texto a buscar. Un % al final de una palabra actúa de comodín para esa palabra.
  • medicalCodingMode=true (por defecto) — solo devuelve entidades con código, que es lo que quieres al codificar.
  • flatResults=true — devuelve una lista plana de coincidencias en lugar de un árbol.
  • useFlexisearch=true — búsqueda laxa: los resultados no tienen por qué contener todas las palabras. Úsalo solo cuando la búsqueda normal no devuelve nada.
  • chapterFilter — restringe a capítulos concretos, por ejemplo 01;02;21.

6.3 Describir un código

6.4 Postcoordinación

La postcoordinación combina un código base («tallo», stem) con uno o varios ejes de extensión. Los caracteres & y / deben ir codificados en la URL (%26 y %2F).

Dos modificadores que necesitarás a menudo:

  • flexiblemode=true — devuelve resultado aunque algunos valores postcoordinados no estén en los conjuntos de valores predefinidos. Los que no se pueden asignar a un eje van bajo otherPostcoordination.
  • convertToTerminalCodes=true — convierte los códigos a los terminales (hojas del árbol), normalmente sustituyéndolos por la residual no especificada del padre.

describe va un paso más allá y puede simplificar la combinación: si existe una entidad precoordinada equivalente, la devuelve.

6.5 Localizar una entidad del Fundamento en la MMS

El lookup es la herramienta clave para traducir entre el Fundamento y la tabla. Devuelve la entidad de la linearización si la entidad del Fundamento está incluida y tiene código; si está incluida pero es un grupo sin código, devuelve la residual no especificada de ese grupo; y si no está incluida, devuelve la entidad a la que se agrega.

6.6 Autocodificación de un texto diagnóstico en español

La respuesta incluye theCode (código encontrado), matchScore (de 0 a 1), matchLevel (el grado de coincidencia) y matchType (la propiedad donde se encontró la coincidencia: Title, Synonym…). Usa matchScore como umbral de confianza en tu flujo: una coincidencia por debajo de tu umbral debería ir a revisión manual.

7.1 Parámetros de búsqueda en ICD-11 MMS

Endpoint: /icd/release/11/{releaseId}/{linearizationname}/search

Parámetros de búsqueda en ICD-11 MMS
Parámetro Endpoint Tipo Predeterminado Descripción

8. Formato de respuesta

8.1 JSON-LD y textos traducibles

La API usa JSON-LD. Los textos que dependen del idioma se devuelven como objetos LanguageSpecificText con dos claves: @language y @value.

No busques title.value ni title.language. Las claves correctas son @value y @language. Es la diferencia entre parsear bien la respuesta y no parsearla nunca.

8.2 Entidades del Fundamento y de la linearización

Esquemas de respuesta principales
Esquema Cuándo lo recibes Campos característicos
FoundationEntity /icd/entity/{id} title, definition, longDefinition, fullySpecifiedName, synonym, inclusion, exclusion, narrowerTerm, child, parent, ancestor, descendant, browserUrl. Sin code.
LinearizationEntity /icd/release/11/{releaseId}/{linearizationname}/{id} Todo lo anterior más code, source, classKind, blockId, codeRange, codingNote, foundationChildElsewhere, indexTerm, postcoordinationScale.
TopLevelFoundation /icd/entity releaseId, releaseDate, availableLanguages, allReleases, supportedLinearizations, child.
TopLevelLinearization /icd/release/11/{releaseId}/{linearizationname} releaseId, releaseDate, availableLanguages, prereleaseLanguages, child (capítulos).

classKind admite estos valores: chapter (capítulo), block (agrupación superior sin código), window (como block pero sin hijos en la linearización) y category (entidad con código).

8.3 Resultados de búsqueda

La búsqueda devuelve un ISearchResult. El campo con las coincidencias se llama destinationEntities (no entities), y cada elemento es un ISimpleEntity:

Campos de una entidad en los resultados de búsqueda
Campo Descripción
id URI de la entidad.
title Título, con la parte coincidente marcada.
code Código (solo en linearizaciones).
isLeaf true si la entidad no tiene hijos.
postcoordinationAvailability Si admite postcoordinación.
hasCodingNote Si lleva nota de codificación.
matchingPVs Propiedades que han coincidido con la búsqueda.
chapter Capítulo al que pertenece.
inclusion / exclusion Términos de inclusión y exclusión.
isResidualOther / isResidualUnspecified Si es una residual «otra» o «no especificada».

A nivel de resultado: uniqueSearchId, guessType, resultChopped (la búsqueda teve demasiados resultados y se truncó), wordSuggestionsChopped, words (las sugerencias de palabra) y error / errorMessage.

8.4 Autocodificación

AutoCodingSearchResult incluye: searchText, matchingText (la mejor frase encontrada), theCode, foundationURI, linearizationURI, matchScore (0 a 1), matchLevel y matchType (la propiedad donde se encontró la coincidencia).

Las propiedades del Fundamento y de las linearizaciones proceden de dos vocabularios: el esquema ICD de la OMS (http://id.who.int/icd/schema/...) y SKOS del W3C (http://www.w3.org/2004/02/skos/core#...).

9. Errores y códigos de estado

Códigos de estado HTTP y la acción recomendada
Código Significado Qué hacer
400 Petición incorrecta (código o URI mal formados, combinación de códigos inválida). Corrige los parámetros. Revisa en especial la codificación de & y /.
401 Falta el token, o el token ha caducado. Pide un token nuevo y repite una vez.
403 El token es válido pero no tiene permisos suficientes. Revisa el ámbito icdapi_access y las credenciales usadas.
404 El recurso no existe (entidad, versión o URI incorrectos). Comprueba el releaseId y la URI.
405 Método no permitido en esa ruta. Usa GET, o POST donde el endpoint lo soporte.
406 No se puede satisfacer la combinación de cabeceras Accept / Accept-Language. Pide application/json y un idioma disponible en esa versión.

500 Error del servidor. Reintenta con espera creciente y, si persiste, comunícalo.

10. Buenas prácticas

  1. Fija la versión. No confíes en «la última versión»: la clasificación cambia entre releases y con ello cambian los códigos. Guarda el releaseId junto a cada dato que almacenes, y a la vista del usuario.
  2. Guarda el idioma junto a la URI. La versión española y la inglesa de una misma categoría tienen URIs distintas. Persiste siempre la pareja (URI, idioma).
  3. Cachéa el token y las respuestas. El token dura una hora; las respuestas de la clasificación cambian solo con los releases. Una caché con clave (endpoint, parámetros, releaseId, idioma) elimina la mayor parte del tráfico.
  4. Usa POST para búsquedas largas. GET tiene un límite de 2 KB.
  5. Codifica & y / en los códigos. GC08&XN62R se envía como GC08%26XN62R.
  6. Pasa los booleanos de forma explícita. medicalCodingMode, flatResults y highlightingEnabled tienen valores por defecto que la documentación describe de forma inconsistente. Escríbelos siempre.
  7. Establece umbrales de confianza en la autocodificación. matchScore va de 0 a 1; por debajo de tu umbral, manda a revisión humana.
  8. Sanea el resaltado. Viene como HTML incrustado en el JSON (sección 8.6).
  9. Reintenta con espera creciente ante 500, y reintenta una sola vez ante 401 renovando el token.
  10. Respeta la clasificación, no solo la API. La ICD-11 es una clasificación viva: sus entidades cambian entre versiones. Revisa las notas de versión antes de una migración: https://icd.who.int/docs/icd-api/ReleaseNotes/.
  11. Registra la versión de la API (API-Version: v2) en tus logs de peticiones: ayuda a diagnosticar cambios de comportamiento tras una actualización.
  12. Para despliegues internos, considera una instancia local (sección 11): sin límites de red y con control total sobre los datos que salen de tu organización.

13.3 Comprobación rápida de la instalación

Si tu integración funciona, estas cuatro comprobaciones deberían cumplirse:

  1. GET /icd/release/11/2025-01/mms responde 200 y su availableLanguages contiene es.
  2. GET /icd/release/11/2025-01/mms/search?q=colera con Accept-Language: es devuelve títulos con @language igual a es.
  3. GET /icd/release/11/2025-01/mms/describe?code=1A00 devuelve una entidad con code 1A00.
  4. GET /icd/release/11/2025-01/mms/lookup?foundationUri=... devuelve la entidad equivalente en la MMS.

Si alguna falla, revisa en este orden: token vigente → API-Version: v2 → Accept: application/json → Accept-Language: es → releaseId válido.
